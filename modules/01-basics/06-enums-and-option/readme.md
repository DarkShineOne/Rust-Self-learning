# Перечисления, match и Option

## Цели

Научиться представлять конечный набор состояний типом, исчерпывающе разбирать варианты и работать с возможным отсутствием значения без `null`.

## Enum как тип-сумма

Struct содержит значения всех своих полей, а enum — ровно один из вариантов:

```rust
enum Delivery {
    Email(String),
    Webhook { url: String, attempt: u32 },
    Disabled,
}
```

Варианты могут содержать tuple-like поля, именованные поля или не содержать данных. Rust выбирает размер enum с учётом самого большого варианта и дискриминанта; не нужно хранить отдельную строку типа и набор необязательных полей.

Для состояний обратной связи enum надёжнее строки: компилятор не даст передать несуществующий `FeedbackStatus::Spam`, если такого варианта нет.

## match

`match` сопоставляет значение с шаблонами и должен быть исчерпывающим:

```rust
let label = match status {
    FeedbackStatus::New => "new",
    FeedbackStatus::InReview => "in_review",
    FeedbackStatus::Resolved => "resolved",
    FeedbackStatus::Rejected => "rejected",
};
```

Можно разбирать вложенные поля, несколько шаблонов через `|` и диапазоны. `_` покрывает оставшиеся случаи, но при моделировании бизнес-правил полное перечисление часто лучше: при добавлении нового статуса компилятор напомнит о каждом затронутом `match`.

`match` возвращает значение, поэтому его удобно ставить после `let` или использовать как результат функции.

## if let и let-else

Если интересен один шаблон, `if let` убирает лишнюю ветку:

```rust
if let Some(rating) = optional_rating {
    println!("{rating}");
}
```

`let-else` подходит для раннего выхода, когда значение не соответствует ожидаемому шаблону:

```rust
let Some(rating) = optional_rating else {
    return;
};
```

Ветка `else` обязана завершить поток управления: `return`, `break`, `continue` или `panic!`. Не заменяйте каждый `match` на `if let`: при нескольких значимых вариантах полный разбор яснее.

## Option вместо null

`Option<T>` — стандартный enum с `Some(T)` и `None`. Значение нельзя использовать как `T`, пока отсутствие не обработано.

- `unwrap_or(default)` возвращает значение или owned default;
- `unwrap_or_else` вычисляет default лениво;
- `map` преобразует содержимое `Some`;
- `and_then` объединяет операции, которые сами возвращают `Option`;
- `as_ref` переходит от `&Option<T>` к `Option<&T>`;
- `ok_or` превращает отсутствие в ошибку `Result`.

`unwrap()` допустим для доказанного инварианта или теста, но не должен заменять обработку пользовательского ввода. `expect("причина")` хотя бы документирует предположение.

## Машина состояний

Переходы статуса удобно описать парами `(self, next)`. Нужно заранее определить идемпотентность: в нашем контракте переход в текущий статус разрешён, терминальные статусы не могут перейти в другой. Такая таблица должна быть единым источником истины, а не разрозненными `if` в HTTP handlers.

В реальной системе enum в БД и JSON требует стабильного строкового представления. Метод `label` отделяет внешний контракт от имени Rust-варианта.

## Option и копирование

`Option<u8>` реализует `Copy`, потому что `u8` реализует `Copy`. `Option<String>` не копируется автоматически: разбор по значению может переместить строку. Если нужно только прочитать содержимое, используйте `match &option` или `as_ref()`.

## Типичные ошибки

- хранить состояние строкой и забывать недопустимые значения;
- добавлять `_` и случайно игнорировать новый вариант;
- вызывать `unwrap()` на внешнем вводе;
- строить глубокие цепочки вложенного `match` вместо `map`/`and_then`;
- разрешать переходы из terminal state без явного правила.
