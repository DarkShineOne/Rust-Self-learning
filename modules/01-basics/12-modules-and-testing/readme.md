# Модули, видимость и тестирование

## Цели

Научиться разделять crate на модули, проектировать публичную границу и выбирать unit, integration или doc test. Практическое задание показывает композицию доменного конструктора и хранилища.

## Пакет, crate и модуль

Пакет Cargo содержит `Cargo.toml`; библиотечный crate начинается с `src/lib.rs`. Модуль организует элементы внутри crate. Объявление `pub mod domain;` подключает `src/domain.rs`, а `pub mod storage;` — `src/storage.rs`.

Пути начинаются с:

- `crate::...` — от корня текущего crate;
- `self::...` — от текущего модуля;
- `super::...` — от родительского модуля;
- имени внешнего crate — от его корня.

`use` создаёт удобное локальное имя, но само по себе не делает элемент публичным. `pub use domain::Feedback` реэкспортирует тип, позволяя пользователям писать `crate_name::Feedback` вместо полного пути.

## Видимость

По умолчанию элемент виден текущему модулю и его потомкам. `pub` открывает его внешним пользователям с учётом видимости всего пути. `pub(crate)` разрешает доступ внутри crate, но не интеграционным тестам как внешним crate.

Приватные поля позволяют поддерживать инвариант: внешний код не может вставить в `MemoryStore` запись мимо `add`. Поле `records` помечено `pub(crate)` для демонстрации внутреннего доступа, но оно не является частью публичного API.

Не путайте видимость Rust с public/private HTTP API итогового проекта. Это разные уровни изоляции.

## Публичный API и зависимости модулей

`domain` не зависит от `storage`: модель не должна знать, где её сохраняют. `storage` использует `crate::domain::Feedback`. Функция верхнего уровня компонует оба модуля. Такое направление зависимостей позже сохранится в веб-сервисе.

Сигнатура `create_feedback` принимает `&mut MemoryStore`, потому что операция меняет конкретное хранилище. Если бы требовались разные реализации, можно было бы применить трейт из урока 10.

## Unit tests

Unit tests располагаются рядом с кодом и имеют доступ к приватным элементам:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn invariant_is_checked() {
        // assert...
    }
}
```

`#[cfg(test)]` включает модуль только при тестовой компиляции. Unit tests подходят для внутренних алгоритмов и граничных состояний, которые не следует делать публичными ради теста.

## Integration tests

Файлы в `tests/*.rs` компилируются как отдельные crate и подключают библиотеку по имени. Они проверяют публичный контракт так же, как это сделает студент или другой сервис.

Каждый файл — отдельный test binary. Общие helpers можно разместить в `tests/common/mod.rs`, чтобы Cargo не считал их самостоятельным тестом. Не добавляйте production-код в `#[cfg(test)]`, если он нужен интеграционным тестам: они используют библиотеку как внешний crate.

## Doc tests

Rustdoc-код в комментариях `///` проверяется `cargo test --doc`. Пометка `no_run` компилирует пример, но не запускает его; `ignore` отключает проверку и должна быть редкостью. Пример домашнего API использует `no_run`, потому что до решения тело содержит `todo!()`.

Документация должна объяснять контракт, ошибки и владение, а не повторять сигнатуру словами.

## Assertions и организация проверок

`assert!` проверяет условие, `assert_eq!` и `assert_ne!` дополнительно показывают значения. `#[should_panic(expected = "...")]` предназначен именно для проверки panic-контракта, а не для превращения любого сбоя в успех.

Хороший тест не зависит от порядка `HashMap`, системной локали и других тестов. Используйте детерминированные fixtures. Название теста должно описывать поведение, например `duplicate_id_does_not_change_existing_record`.

Cargo по умолчанию запускает тесты параллельно. Общие файлы, БД и переменные окружения требуют изоляции, а не глобального `--test-threads=1` как единственного решения.

## Типичные ошибки

- делать всё `pub` ради тестов;
- циклические зависимости domain ↔ storage;
- дублировать бизнес-правила в handler и storage;
- использовать `should_panic` для обычного `Result::Err`;
- помещать общий helper в `tests/common.rs`, создавая лишний test binary.
