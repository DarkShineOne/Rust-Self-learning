# Консольный CRUD обратной связи

## Цели

Объединить владение, типы, ошибки, итераторы, трейты и модули в небольшом законченном приложении. Главная задача — не написать парсер любой ценой, а разделить ответственность так, чтобы доменные правила можно было проверить без терминала.

## Слои приложения

В проекте три уровня:

1. `Feedback`, `NewFeedback`, `UpdateFeedback`, `FeedbackStatus` — модель и инварианты.
2. `FeedbackService<R>` — сценарии create/read/update/delete, переходы статуса и генерация id.
3. `JsonFileRepository` — представление записей в JSON и работа с файловой системой.

`run_cli` — адаптер командной строки. Он преобразует строки в типы и выводит JSON, но не должен дублировать правила сервиса. `src/main.rs` только читает аргументы и путь к файлу.

Направление зависимостей: CLI зависит от service, service — от интерфейса repository, реализация файла — от типов модели. Домен не импортирует CLI.

## CRUD как контракт

Create возвращает созданную сущность, а не просто успех. Read включает получение одной записи и списка. Update применяет только переданные `Some`-поля, сохраняя остальные. Delete возвращает удалённую запись.

Отсутствие id — `NotFound`, а не panic и не пустая сущность. Ошибки ввода — конкретные варианты `ServiceError`. Любая ошибка до мутации не должна менять файл.

`list` сортирует результат по id, чтобы CLI и тесты были детерминированы. ID новой записи вычисляется как текущий максимум плюс один. Такой алгоритм подходит только для однопользовательского учебного файла; в PostgreSQL генерацией и уникальностью будет управлять база.

## Generic service и трейт repository

`FeedbackService<R: FeedbackRepository>` зависит от поведения, а не конкретного пути. Для unit-тестов можно создать in-memory repository, для CLI — JSON repository.

Трейт использует `&self`, потому что вызывающий код работает с общим сервисом. Это не означает thread safety: отдельный CLI-процесс владеет сервисом, а файловая реализация не обещает конкурентную синхронизацию процессов.

Метод `save(&self, feedback: &[Feedback])` принимает срез: репозиторий читает записи и сериализует их, не забирая владение у сервиса. `load` возвращает owned `Vec<Feedback>`, поскольку десериализация создаёт новые данные.

## Serde и граница данных

`Serialize` и `Deserialize` описывают преобразование типов в формат. `#[serde(rename_all = "snake_case")]` делает статусы `new`, `in_review`, `resolved`, `rejected` в JSON.

Serde derive не валидирует бизнес-правила. JSON с `rating: 99` может успешно превратиться в `Feedback`, если поле `u8`. Доверять такому файлу нельзя; в учебном проекте важно отличать syntactic validation формата от доменной валидации.

`serde_json::Error` и `std::io::Error` преобразуются в `ServiceError::Storage`. Сохраняйте причину в строке для CLI, но не раскрывайте её как точный машинный вариант домена.

## Файловая семантика

Отсутствие файла означает новое пустое хранилище. Другие ошибки чтения — permissions, directory вместо файла, невалидный JSON — являются `Storage`, а не пустым списком. Иначе приложение могло бы перезаписать реальные данные после ошибки чтения.

`save` записывает pretty JSON. В настоящем приложении стоит добавить atomic write через временный файл и rename, fsync/backup по требованиям и обработку конкурентных процессов. Здесь эти ограничения явно оставлены за рамками задания.

Не создавайте родительские каталоги неявно: если их нет, верните `Storage`. Путь передаётся в `JsonFileRepository::new` и доступен через `path()`.

## Workflow статуса

Машина состояний повторяет урок 06:

- переход в текущий статус разрешён;
- `New → InReview | Rejected`;
- `InReview → Resolved | Rejected`;
- `Resolved` и `Rejected` терминальны для другого статуса.

Проверка должна предшествовать изменению записи. При `InvalidTransition` файл и запись остаются прежними.

## CLI как тонкий адаптер

Пример будущего запуска после реализации:

```bash
cargo run -p basics-15-console -- create "Title" "Body" 5
cargo run -p basics-15-console -- list
cargo run -p basics-15-console -- status 1 in_review
```

`FEEDBACK_FILE` задаёт путь; по умолчанию используется `feedback.json`. Главный бинарник уже содержит только передачу аргументов и печать результата. Вся реализация остаётся в тестируемой библиотеке.

`run_cli` возвращает JSON через `serde_json`, чтобы тесты могли разобрать результат вместо сравнения декоративного текста. Ошибка команды сохраняет исходные аргументы через `args.join(" ")`.

## Как подойти к реализации

1. Реализуйте `can_transition_to` и repository.
2. Напишите validation helper как приватную функцию, если это уменьшает дублирование.
3. Реализуйте service, проверяя тесты после каждой операции.
4. Только затем подключите CLI.
5. Проверьте ошибки и повторную загрузку из нового экземпляра service.

Не меняйте трейт ради удобства одной функции. Если не хватает helper, сделайте его приватным внутри impl или модуля.

## Критерии ревью

- нет дублирования правил в CLI и service;
- ошибки сохраняют варианты `ServiceError`;
- отсутствие файла отличается от повреждённого файла;
- нет `unwrap()` на пользовательском вводе и I/O;
- нет ненужного клонирования всего хранилища сверх `load`/save модели;
- исходные записи не меняются при неуспешной операции.
