# Result и обработка ошибок

## Цели

Научиться отличать ожидаемые ошибки от нарушенных инвариантов, проектировать содержательный enum ошибок и распространять ошибки оператором `?` без вложенных `match`.

## Option или Result

`Option<T>` сообщает только о наличии значения. `Result<T, E>` добавляет причину неуспеха:

```rust
fn parse_rating(input: &str) -> Result<u8, std::num::ParseIntError> {
    input.parse::<u8>()
}
```

Поиск по ключу естественно возвращает `Option`, разбор внешнего текста обычно возвращает `Result`. Метод `ok_or` превращает `Option` в `Result`, а `.ok()` намеренно отбрасывает ошибку.

## Recoverable и panic

Ошибка пользовательского ввода, недоступность БД и отсутствие файла — ожидаемые события. Их нужно представить `Result` и обработать на подходящем уровне.

`panic!` предназначен для нарушенного внутреннего инварианта, от которого текущий код не может осмысленно восстановиться. `unwrap()` и `expect()` вызывают panic при ошибке. В тестах `unwrap()` лаконичен, потому что неуспех теста и есть нужное поведение. В сетевом handler такой вызов может завершить задачу или процесс и не заменяет HTTP error response.

## Распространение через ?

`?` завершает текущую функцию при `Err`, а при `Ok` извлекает значение:

```rust
fn read_config(path: &std::path::Path) -> Result<String, std::io::Error> {
    let text = std::fs::read_to_string(path)?;
    Ok(text)
}
```

Тип ошибки должен поддерживать преобразование через `From`, если он отличается от ошибки текущей функции. `?` также работает с `Option`, но нельзя без явного преобразования применять его к `Result` в функции, возвращающей `Option`.

Возврат последнего `Ok(...)` — нормальный способ указать тип результата. Не путайте `?` с `.unwrap()`: первый возвращает ошибку вызывающему коду, второй паникует.

## Собственный enum ошибок

Ошибки предметной области должны отражать варианты отказа и сохранять полезный контекст:

```rust
#[derive(Debug)]
enum ConfigError {
    MissingPort,
    InvalidPort(std::num::ParseIntError),
}
```

Реализация `Display` задаёт пользовательское сообщение, `std::error::Error::source` — цепочку причин. В курсе `thiserror::Error` генерирует эти реализации через атрибуты `#[error("...")]`, оставляя варианты явными.

Не включайте пароли, токены и секретные заголовки в ошибку. Не показывайте внутреннюю цепочку внешнему клиенту без фильтрации: логи и публичный ответ имеют разную аудиторию.

## thiserror и anyhow

`thiserror` удобен для библиотек и доменных ошибок, когда вызывающий код должен различать варианты. `anyhow` часто используют на границах приложения для объединения разных ошибок с контекстом. Это не конкурирующие обязательные слои: сначала определите, нужен ли потребителю конкретный тип ошибки.

Для учебного парсера тесты сравнивают точные варианты `CommandError`, поэтому `String` в качестве всего типа ошибки уже недостаточен.

## Преобразование ошибок

`map_err` явно меняет тип ошибки и позволяет добавить контекст. `From` делает преобразование автоматическим под `?`. Не скрывайте класс ошибки: нарушение уникальности нельзя превращать в «внутреннюю ошибку», если API должен ответить 409.

В транзакционных системах ошибка также влияет на commit/rollback. Сообщение об ошибке не означает, что побочные эффекты отменены, — это нужно проектировать отдельно.

## Коллекция Result

Итератор над `Result<T, E>` можно собрать в `Result<Vec<T>, E>`. Сборка остановится на первой ошибке. При этом уже выполненные чистые вычисления не откатываются, но итоговый `Vec` не возвращается. Если ошибки нужно собрать все, потребуется другой алгоритм.

## Типичные ошибки

- использовать panic для обычного invalid input;
- превращать все ошибки в одинаковую строку;
- молча отбрасывать `Result` через `let _ = ...`;
- терять исходную причину при `map_err`;
- показывать SQL и внутренние адреса пользователю API.
