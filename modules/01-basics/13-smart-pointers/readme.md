# Умные указатели и внутренняя изменяемость

## Цели

Научиться выбирать `Box`, `Rc`, `Arc`, `RefCell`, `Mutex` и `RwLock` по требованиям владения и конкурентности. Понять, что разделяемое владение не означает автоматическую безопасную мутацию.

## Box

`Box<T>` владеет значением в куче и имеет одного владельца. Основные применения: большие значения, рекурсивные типы, trait objects `Box<dyn Trait>`, перенос владения с известным размером `Box`.

Рекурсивный `enum Node { Next(Node) }` имел бы бесконечный размер, а `Next(Box<Node>)` содержит указатель фиксированного размера. Box не добавляет подсчёт ссылок и не разделяет владение.

`Deref` позволяет умному указателю вести себя как ссылка на внутреннее значение. `DerefMut` даёт изменяемый доступ при наличии уникального доступа к указателю. Не реализуйте `Deref` только ради удобного наследования API — это не механизм наследования.

## Drop

`Drop::drop` вызывается автоматически при уничтожении владельца. Ресурсы RAII освобождаются без отдельного `free`. Ручной вызов `.drop()` запрещён, но `std::mem::drop(value)` досрочно завершает владение.

Владение lock guard также основано на Drop: при выходе guard из области видимости блокировка освобождается. Поэтому важно понимать, где guard живёт и когда его нужно явно убрать.

## Rc и Arc

`Rc<T>` подсчитывает сильные ссылки в одном потоке. Клон Rc создаёт нового владельца того же значения, а не клон `T`. Последний уничтоженный Rc освобождает значение.

`Arc<T>` решает аналогичную задачу с атомарным подсчётом и может передаваться между потоками, если само `T` удовлетворяет необходимым `Send`/`Sync`. `Arc::strong_count` возвращает текущее число сильных ссылок и полезен для обучения, но не должен управлять бизнес-логикой.

Ни Rc, ни Arc сами по себе не разрешают безопасно менять содержимое при разделяемых ссылках.

## RefCell

`RefCell<T>` переносит проверку заимствования в runtime: `borrow()` возвращает read guard, `borrow_mut()` — exclusive guard. Нарушение правил вызывает panic. RefCell не предназначен для потоков.

Это полезно в однопоточных структурах, когда компилятор не может доказать дисциплину доступа, а разработчик поддерживает её сам. Частый `Rc<RefCell<T>>` в веб-сервисе — признак того, что стоит пересмотреть модель владения.

## Mutex и RwLock

`Mutex<T>` допускает одного держателя доступа. `RwLock<T>` допускает множество readers либо одного writer. В стандартной библиотеке `lock()`/`read()`/`write()` возвращают `Result` с lock guard, поскольку предыдущая panic во время удержания lock могла отравить его.

`Poisoned` в домашнем enum сохраняет эту возможность. Не используйте автоматически `into_inner()` у poisoned guard: сначала решите, действительно ли инвариант данных не нарушен.

Типичный shared store — `Arc<RwLock<HashMap<...>>>`:

```rust
use std::sync::{Arc, RwLock};
let value = Arc::new(RwLock::new(0));
let clone = Arc::clone(&value);
*clone.write().expect("lock") += 1;
assert_eq!(*value.read().expect("lock"), 1);
```

Здесь `expect` демонстрирует учебный инвариант, а в задании poisoning преобразуется в `StoreError`.

## Guard и возвращаемые ссылки

Нельзя вернуть `&Feedback` из `HashMap` после уничтожения read guard: данные защищены lock только пока жив guard. Поэтому задание возвращает клон записи. Альтернативы — вернуть собственный тип guard, изменить API на callback или хранить записи в Arc, но каждый вариант имеет цену.

Это пример осмысленного Clone: копия небольшой записи позволяет сразу освободить блокировку.

## Циклы ссылок и Weak

`Rc`/`Arc` не собирают циклы сильных ссылок. Если родитель владеет детьми, а дети родителем, память может не освободиться. `Weak<T>` предоставляет неконтролирующую ссылку, которую нужно `upgrade()` до временного Rc/Arc. Это не универсальная сборка мусора, а явный способ разорвать цикл.

## Критерии выбора

- одно владение в куче — `Box`;
- разделяемое однопоточное чтение — `Rc`;
- разделяемое многопоточное владение — `Arc`;
- однопоточная interior mutability — `RefCell`;
- синхронная многопоточная мутация — `Mutex`/`RwLock`;
- async critical section с await — отдельно оценить Tokio lock в уроке 14.

## Типичные ошибки

- считать `Arc<T>` клоном данных `T`;
- менять данные через `Arc` без синхронизации;
- возвращать ссылку из-под уничтоженного guard;
- использовать `RefCell` в многопоточном сервере;
- удерживать lock при длительной работе или вызове неизвестного кода.
