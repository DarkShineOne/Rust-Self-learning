# JSON, extractors и валидация

## Цели

Научиться отделять транспортный DTO от проверенных данных, обрабатывать частичные обновления и возвращать предсказуемые JSON-ошибки. Serde решает синтаксическую задачу, но не знает бизнес-правил.

## DTO и доменная модель

`CreateFeedback` описывает именно JSON запроса: title, body, rating и category. В нём нет `id`, `status`, `author_id` и `role`, потому что эти значения определяет сервер. Если разрешить клиенту заполнять их напрямую, появится mass assignment и эскалация прав.

Отдельный `ValidatedFeedback` показывает, что проверка уже пройдена. Такой pattern называют «make invalid states unrepresentable» на уровне границы: handlers дальше по цепочке не должны повторно гадать, прошли ли значения нормализацию и проверку диапазона.

В большом приложении DTO и доменная сущность обычно различаются сильнее. Не сериализуйте запись БД напрямую только потому, что поля временно совпали.

## Serde derive

`Deserialize` строит значение из JSON, `Serialize` формирует ответ. `#[serde(rename_all = "snake_case")]` преобразует имена вариантов enum.

`#[serde(deny_unknown_fields)]` отклоняет неизвестные поля. Это помогает обнаружить опечатки и попытку передать запрещённое поле, но требует более аккуратной эволюции API. Публичный контракт должен фиксировать такое поведение.

`Option<T>` принимает отсутствие поля или JSON null как `None`. Для PATCH это не всегда позволяет отличить «поле не передано» от «передан null». При необходимости тройного состояния используют дополнительный подход, например двойной Option с явной семантикой.

## Json extractor

`Json<CreateFeedback>` читает тело и проверяет content type по правилам Axum. Ошибка десериализации превращается в rejection до входа в handler. Для production API можно создать собственный extractor, чтобы rejection тоже имел общий Problem Details формат.

Extractors реализуют `FromRequest` или `FromRequestParts` в зависимости от потребления тела. Порядок аргументов важен: body-consuming extractor должен быть последним.

## Нормализация и валидация

Сначала определите правила: в задании title/body сохраняются после `trim()`, внутренние пробелы не меняются. Проверка длины выполняется `.chars().count()`, а не `.len()`, потому что контракт говорит о символах.

Проверка Create идёт в порядке title empty/too long, body empty/too long, rating. Для Update сначала определяется наличие хотя бы одного `Some`, затем проверяются только присутствующие поля в том же порядке.

`Some("   ")` — присутствующее, но невалидное значение. `None` означает отсутствие изменения, а не очистку строки.

Не применяйте бездумно одинаковый trim к email, паролю и тексту. Пароль может содержать значимые краевые пробелы по политике приложения, а email требует отдельного канонического представления.

## HTTP status для ошибок

В учебном handler доменная ошибка валидации превращается в `422 Unprocessable Entity` с телом `{"error":"..."}`. Некорректный JSON отклоняется extractor-ом отдельно и не должен вызывать доменный `validate`.

400 часто означает malformed request, 422 — синтаксически читаемые данные, не прошедшие семантическую проверку. В реальном API важно выбрать согласованную политику и задокументировать её.

`201 Created` сопровождает успешное создание. Здесь handler возвращает проверенный DTO, а не полноценную сущность с БД; это учебная граница до следующего урока.

## Безопасность входных данных

Валидация не заменяет параметризованные SQL запросы и экранирование на выходе. Не «санируйте HTML» заранее, если клиентам нужен исходный текст: храните данные корректно и учитывайте контекст отображения.

Ограничение длины поля не ограничивает общий размер HTTP body до чтения. Для него нужен transport limit, добавленный в уроке 12.

## Тестирование валидации

Проверяйте не только отказ, но и конкретный вариант ошибки. Границы 100/2000 символов тестируются значениями ровно на границе и на единицу больше. Добавьте Unicode, whitespace и пустое обновление.

Route tests дополнительно проверяют, что handler действительно использует validate, возвращает 201/422 и сериализует ожидаемый JSON.

## Типичные ошибки

- разрешать клиенту `author_id` и `role`;
- считать длину в байтах вместо символов;
- считать `None` и пустую строку одинаковыми;
- смешивать ошибку JSON и доменную 422;
- валидировать только в тестах или только в UI, минуя серверный handler.
