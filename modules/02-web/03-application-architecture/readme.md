# Архитектура приложения

## Цели

Разделить HTTP, бизнес-правила и хранение, передавать состояние Axum без глобальных mutable static и тестировать сервис отдельно от router. In-memory реализация здесь нужна как учебный адаптер, а не как замена PostgreSQL в итоговом проекте.

## Слои и зависимости

`Feedback` и DTO описывают данные. `FeedbackService` реализует сценарии и инварианты. `FeedbackRepository` задаёт необходимые сервису операции хранения. `MemoryRepository` реализует их через HashMap. Handlers преобразуют HTTP в вызовы сервиса и ошибки сервиса в HTTP.

Зависимости направлены внутрь: handler знает service, service знает абстракцию repository, конкретная память реализует трейт. Домен не должен импортировать Axum или SQLx.

Если handler сам проверяет рейтинг, ищет по map и формирует ID, следующий адаптер БД заставит переписать HTTP. Слой service устраняет это дублирование.

## Repository и async_trait

Async repository нужен для I/O. Макрос `async_trait` преобразует async методы в форму, совместимую с trait objects и одинаковым синтаксисом реализаций. В современном Rust async fn в traits существует нативно, но динамическая диспетчеризация и точные Send-ограничения требуют дополнительного внимания.

`FeedbackRepository: Send + Sync` позволяет разделять реализацию между задачами. Сервис хранит `Arc<R>`, поэтому клонирование Arc не копирует map.

Сигнатуры repository не содержат HTTP status. `NotFound` — доменный результат, а 404 появляется только на границе API.

## Service владеет правилами

Create нормализует и проверяет DTO до вызова repository. Update сначала получает существующую запись, применяет `Some`-поля и проверяет новое целое. Только затем вызывает `replace`.

`None` не меняет поле. Пустой Update возвращает текущую запись; service не создаёт фиктивную мутацию. При невалидном значении `replace` не вызывается.

Проверка в service не мешает repository сохранять собственные инварианты: `replace` отсутствующего id возвращает NotFound, а не вставляет запись. Это защищает контракт при другом вызывающем коде.

## ID и конкурентность

`AtomicU64` выделяет следующий id без отдельной блокировки всей map на операцию fetch_add. Начальное значение 1. `fetch_add` возвращает предыдущее значение, что нужно учесть при выборе инициализации.

`RwLock<HashMap>` защищает записи. Каждая операция клонирует результат и освобождает guard до возврата. Не удерживайте guard через внешний await.

В учебном repository создание сущности и атомарный ID просты, но даже здесь нужно решить порядок получения ID и write lock. В PostgreSQL эти задачи распределяются иначе: identity/UUID и constraint проверяются базой.

## AppState и Arc

Axum `State<AppState>` передаёт состояние handlers. `AppState` Clone, поэтому каждый handler получает ссылку на общие Arc-компоненты, а не независимый репозиторий.

Не используйте `static mut` для состояния. Глобальное состояние усложняет тесты и lifecycle. `AppState::new` создаёт новый независимый graph зависимостей для каждого теста.

В дальнейшем state будет включать pool PostgreSQL, HTTP client, S3 storage и конфигурацию JWT. Слоистая структура остаётся той же.

## Handlers и ошибки

Handler отвечает за extraction, вызов service и статус. Create возвращает 201, остальные успешные операции — 200. `ApiError` хранит статус и безопасное сообщение, а `IntoResponse` формирует единый JSON.

`From<ServiceError>` использует отдельную функцию `status_code`. Это учебное упрощение: в итоговом проекте появится Problem Details и внутренние ошибки, сообщения которых нельзя показывать напрямую.

Router принимает state параметром. Это позволяет route-тестам строить новое состояние, а не делить глобальную map между тестами.

## Тестовая стратегия

Service tests используют MemoryRepository напрямую и не создают HTTP. Они проверяют нормализацию, ошибки и CRUD. Route tests используют `AppState::new` и `oneshot`, проверяя маршрутизацию, extraction, статус и JSON.

Repository tests можно отделить от service tests, но в маленьком пакете сочетание допустимо. Не тестируйте приватные поля map: контрактом являются публичные операции.

После замены памяти на PostgreSQL большая часть service tests должна остаться, если зависимость можно заменить mock-репозиторием. Интеграционные тесты SQL отдельно проверяют адаптер.

## Типичные ошибки

- SQL в handler;
- HTTP status в доменном enum;
- новый MemoryRepository для каждого handler;
- `Arc` без внутренней синхронизации изменяемой map;
- update через insert-или-replace;
- возврат 500 с текстом любой ошибки.
