# Подключение внешнего HTTP API

## Цели

Научиться создавать типизированный Reqwest client, задавать timeout и credentials, обрабатывать статусы и ограниченно повторять безопасные запросы. Внешний сервис уведомляет модераторов о новой обратной связи; тесты используют локальный mock server, а не интернет.

## Граница внешнего сервиса

`HttpNotifier` скрывает URL, заголовки, JSON-формат и retry от domain service. Сервис обратной связи передаёт `Notification`, а не `reqwest::Request`. Это позволяет заменить клиент mock-реализацией и не привязывает домен к Reqwest.

Endpoint: `POST {base_url}/v1/notifications`. Base URL приходит из доверенной конфигурации, а не из текста обращения. Если URL может задавать пользователь, нужна отдельная защита от SSRF: ограничение схемы, адресов, redirects и внутренних сетей.

`Authorization: Bearer <api_key>` хранится в конфигурации и не логируется. `Idempotency-Key: feedback-<id>` позволяет получателю распознать повторную доставку события.

## Client и timeout

`reqwest::Client` стоит создавать один раз и клонировать handle, а не строить для каждого запроса: внутри переиспользуются соединения и настройки.

Timeout обязателен. Без него внешняя неисправность может удерживать handler и пул ресурсов. `ClientBuilder::timeout` ограничивает запрос, но при retry общее время операции возрастает: учитывайте `attempts × timeout` и задержки backoff.

В задании нет sleep/backoff для простоты тестов. В production обычно добавляют exponential backoff с jitter и общий deadline. Не копируйте учебный немедленный retry как универсальную политику.

## Что повторять

Разрешены только дополнительные попытки для:

- timeout и ошибок соединения/transport, когда это имеет смысл;
- HTTP 502, 503, 504.

Не повторяем 400, 401, 403, 404, 409, 422 и другие не retryable статусы. `max_retries` считает дополнительные попытки после первой, поэтому всего возможно `max_retries + 1` запросов.

Даже POST можно повторять здесь только благодаря Idempotency-Key и контракту получателя. Таймаут не доказывает, что сервер не обработал первый запрос. Без idempotency retry может создать дубликат.

## Обработка ответа

2xx ответ декодируется в `NotificationResponse`. `accepted: false` — доменный Rejected. Некорректный JSON — InvalidResponse. Retryable статус после исчерпания попыток — ServerStatus, остальной статус — UnexpectedStatus.

`reqwest::Error::is_timeout` помогает отличить Timeout. Другие transport errors сохраняются в сообщении, но URL с credentials и headers нельзя выводить в логи.

Не используйте `error_for_status` как единственную логику: для retry и понятных ошибок нужны сами status codes.

## Ошибка внешнего API в бизнес-операции

Нужно заранее решить, откатывается ли создание feedback при сбое уведомления. Обычно нельзя распределить PostgreSQL и HTTP в одну транзакцию. Варианты: принять обращение и повторить уведомление позже, сохранить outbox, вернуть 503 без создания, либо принять частичный успех с явным статусом.

В итоговом проекте контракт фиксирует обработку сбоя и тестирует её. Не скрывайте неуспех, просто написав `let _ = notify(...).await`, если модераторы обязаны получить событие.

## Mock server

`wiremock` запускает локальный HTTP server и позволяет задать ожидания method/path/header/body, response status/json/delay и точное число вызовов. Так проверяются:

- правильный endpoint и Bearer;
- идемпотентный ключ;
- отсутствие retry на 500;
- ровно `max_retries + 1` попыток на 503;
- timeout и malformed response.

Mock не проверяет реальную совместимость с провайдером. Для неё нужен отдельный contract test в контролируемой среде, но CI не должен зависеть от публичного интернета.

## TLS и redirects

Production endpoint должен использовать HTTPS. Самоподписанные сертификаты и отключение проверки TLS не являются нормальным решением. Redirects могут перенести Authorization на другой хост; ограничьте политику или отключите их для чувствительного клиента.

Не сериализуйте секрет в Debug. NotifierConfig в заготовке Clone и Debug для учебного кода, но в рабочем приложении лучше ручной redacted Debug и secret wrapper.

## Типичные ошибки

- отсутствие timeout;
- бесконечный retry;
- повтор всех статусов и неидемпотентных операций;
- новый Client на каждый запрос;
- внешний вызов внутри DB transaction;
- секреты в логах;
- тесты против реального публичного API.
