# HTTP, REST и первый Axum-сервис

## Цели

Понять базовый контракт HTTP, связать Tokio runtime с Axum Router и протестировать handler без реального сетевого порта. В задании только один endpoint, но используемый подход сохранится до итогового проекта.

## HTTP как контракт

Запрос содержит метод, target, заголовки и необязательное тело. Ответ — status code, заголовки и тело. Метод имеет семантику:

- `GET` читает представление и не должен менять ресурс;
- `POST` создаёт ресурс или запускает операцию по контракту;
- `PATCH` частично изменяет ресурс;
- `DELETE` удаляет ресурс;
- `PUT` обычно заменяет представление по известному URI.

Success codes должны быть конкретными: `200 OK` для чтения, `201 Created` для создания, `204 No Content` для успеха без тела. Клиентские ошибки 4xx отличаются от серверных 5xx. Не возвращайте 200 с `{"error":...}` при неуспехе.

REST использует ресурсы и представления. `/feedback/{id}` адресует конкретное обращение, а HTTP-метод определяет операцию. Не нужны пути `/createFeedback` и `/deleteFeedback`, если достаточно стандартной семантики.

Idempotent operation при повторном идентичном вызове имеет тот же предполагаемый эффект на сервере. Это не означает одинаковый response body или отсутствие логов. Retry особенно важно учитывать при сетевых таймаутах.

## Tokio и Axum

Tokio предоставляет runtime, timers, TCP и синхронизацию. Axum строит HTTP API поверх Tower и Tokio:

```rust
use axum::{routing::get, Router};
let application = Router::new().route("/health", get(|| async { "ok" }));
```

`Router` сопоставляет метод и путь с handler. Handler — async-функция из extractor-ов, возвращающая тип `IntoResponse`. В Axum 0.8 параметры пути записываются как `/{id}`, а не `/:id`.

`#[tokio::main]` запускает runtime для `main`. `TcpListener` принимает соединения, `axum::serve` обслуживает их. Не вызывайте блокирующий runtime внутри уже работающего runtime.

## Json и IntoResponse

`Json<T>` как extractor десериализует тело запроса, а как response сериализует `T` и добавляет `Content-Type: application/json`. Тип должен реализовать соответствующие Serde-трейты.

Кортеж `(StatusCode, Json<T>)` позволяет задать статус. `&'static str` и `String` становятся текстовым ответом. Для ошибок позже появится собственный `IntoResponse`, чтобы формат был единым.

## Тестирование без порта

`Router` реализует Tower `Service<Request<Body>>`. `tower::ServiceExt::oneshot` передаёт один запрос напрямую приложению:

```rust,ignore
let response = application.oneshot(request).await?;
```

Не используются TCP-порт и внешний процесс, поэтому тест быстрый и детерминированный. Тело ответа собирается через `http_body_util::BodyExt::collect`, затем разбирается `serde_json`.

`oneshot` потребляет service, поэтому для нескольких запросов клонируйте Router. Клонирование Axum Router дешёвое по сравнению с созданием нового разделяемого состояния.

## Graceful shutdown

В реальном сервисе `with_graceful_shutdown` получает future, завершение которой останавливает приём новых соединений и даёт текущим запросам завершиться. На Unix обычно обрабатывают SIGTERM и Ctrl-C, на Windows — Ctrl-C и события службы по требованиям.

Shutdown не заменяет timeout: зависший запрос способен задержать остановку. В уроке 12 мы добавим явные пределы и логирование.

## Health endpoints

`GET /health` учебного урока только подтверждает работу router. В итоговом проекте liveness отвечает, что процесс работает, а readiness — что сервис готов принимать трафик и необходимые зависимости доступны.

Health не должен раскрывать credentials, строку подключения или внутренние ошибки с секретами. Детальная диагностика отправляется в защищённые логи.

## Типичные ошибки

- регистрировать неправильный метод и получать 405;
- путать 404 отсутствия маршрута и 404 отсутствия ресурса;
- ожидать JSON response без `Serialize`;
- запускать второй runtime внутри Tokio;
- считать успешный TCP bind доказательством готовности зависимостей.
