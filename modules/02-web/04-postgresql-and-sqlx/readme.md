# PostgreSQL и SQLx

## Цели

Научиться подключать SQLx pool, отделять конфигурацию от кода, писать миграции и проверять соединение настоящей PostgreSQL. В этом уроке нет SQLite-замены: типы, constraints и поведение транзакций должны проверяться на целевой СУБД.

## Реляционная модель

Таблица users хранит учётные записи, feedback — обращения. `author_id` является foreign key и связывает каждое обращение с автором. Ограничения не дают сохранить некорректные данные даже мимо Rust service.

Primary key идентифицирует строку, unique constraint запрещает дубликаты email, check constraints ограничивают rating и role/status. Foreign key с `ON DELETE RESTRICT` не позволяет удалить автора вместе с непредусмотренной потерей обратной связи.

Не полагайтесь только на check в приложении: ручной SQL и другой сервис могут обойти его. Но и ошибки constraints нужно преобразовывать в понятный доменный результат.

## Pool соединений

`PgPool` управляет набором соединений. Его клонирование создаёт handle к тому же pool, поэтому pool удобно хранить в AppState. Не создавайте новый pool на каждый HTTP запрос.

`PgPoolOptions` задаёт max_connections. Число зависит от лимитов PostgreSQL и количества экземпляров приложения: 10 экземпляров по 20 соединений — это уже 200 потенциальных соединений.

`connect` ожидает установление соединения. `healthcheck` выполняет минимальный SQL. Наличие pool handle ещё не доказывает доступность сервера.

## DATABASE_URL и секреты

`DATABASE_URL` содержит хост, порт, базу, пользователя и пароль. Его нельзя печатать в логах и включать в публичную ошибку. В репозитории допустимы только локальные учебные значения Compose, не production credentials.

`DatabaseConfig::from_env` читает URL и `DB_MAX_CONNECTIONS`, по умолчанию 5. `DatabaseConfig::new` отдельно проверяет уже полученные значения, чтобы валидацию можно было тестировать без глобальных переменных окружения.

Не используйте параллельные тесты, меняющие `DATABASE_URL`: это общее состояние процесса. Передавайте конфигурацию параметром.

## SQLx queries

`sqlx::query`, `query_as` и `query_scalar` принимают SQL и параметры:

```rust,ignore
sqlx::query_scalar::<_, i64>("SELECT 1::BIGINT")
    .fetch_one(pool)
    .await?;
```

Для параметров используются `bind` и placeholders `$1`, `$2`. Никогда не собирайте значения пользователя в SQL через `format!`: параметризация предотвращает SQL injection и корректно передаёт типы.

Макросы `query!`/`query_as!` дополнительно проверяют SQL на этапе компиляции. Им нужна доступная БД или подготовленные offline-данные `.sqlx`. В учебных заготовках используются runtime-методы, чтобы workspace собирался без базы; принцип параметризации одинаков.

## Миграции

Миграция — версионированное изменение схемы. SQLx хранит журнал применённых версий в служебной таблице. `sqlx::migrate!()` встраивает файлы из каталога `migrations`, `.run(pool).await` применяет недостающие.

После применения миграцию в общей истории не переписывают. Новые изменения оформляют следующей миграцией. Перед production применением нужны backup, оценка блокировок и совместимость старого/нового кода во время rolling deploy.

Заготовка содержит только комментарий. Студенту нужно написать SQL самостоятельно по контракту домашнего задания.

## Типы PostgreSQL и Rust

`BIGINT` соответствует `i64`, `TEXT` — `String`, `TIMESTAMPTZ` — `DateTime<Utc>` при включённой feature chrono. `SMALLINT` — `i16`. Nullable колонка обычно представляется `Option<T>`.

`SERIAL` удобен в примерах, но explicit identity columns лучше выражают современный SQL. Используйте `GENERATED ALWAYS AS IDENTITY`, если не собираетесь разрешать ручное присвоение id.

`NOW()` возвращает текущий timestamp. Для updated_at значение меняется при update через SQL или надёжный механизм приложения; простой default задаёт только создание.

## Integration tests

`#[sqlx::test]` создаёт изолированную тестовую базу и предоставляет `PgPool`. Опция `migrations = "./migrations"` применяет миграции crate. Тестам нужен `DATABASE_URL` с правами создавать и удалять тестовые базы.

Изолированность важнее глобального последовательного запуска. Не используйте production URL для тестов. В документации задания приведён локальный URL из Compose.

Docker сейчас может отсутствовать на машине студента; тогда unit tests конфигурации доступны, а database tests выполняются после самостоятельной установки PostgreSQL.

## Типичные ошибки

- новый pool на каждый запрос;
- SQL через `format!` с пользовательским вводом;
- логирование полного DATABASE_URL;
- nullable колонка без `Option`;
- отсутствие FK/check constraints;
- изменение уже применённой миграции;
- тесты против общей базы разработки.
